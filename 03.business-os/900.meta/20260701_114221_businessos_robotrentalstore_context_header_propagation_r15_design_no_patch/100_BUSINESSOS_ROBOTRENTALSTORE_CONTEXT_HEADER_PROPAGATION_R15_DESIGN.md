## Design decision

- HEADER_PROPAGATION_MODE: FETCH_BOUNDARY_SAFE_HEADER_MERGE_DESIGN
- R16_RECOMMENDATION: PATCH_STATIC_FETCH_BOUNDARIES_AFTER_GO

## Principle

Header propagation must happen only at the browser request boundary.

Do not make page-load side effects.
Do not call fetch merely to test context.
Do not enforce login.
Do not verify sessionRef in the browser.
Do not treat sessionRef as a credential.
Do not expose civilizationId/sessionRef in visible UI.
Do not pass password/token/secret/DB URL fields.

## Safe headers

The only designed headers are:

- x-civilization-id
- x-owner
- x-civilization-session-ref
- x-locale-code
- x-language-code
- x-requested-os-code
- x-return-to
- x-after-login-path

## Merge rule

When a RobotRentalStore static page makes an API request, merge headers from:

```js
window.BusinessOSCivilizationContext.getHeaders()
```

into the request headers.

Caller-provided headers must remain supported.
Civilization context headers must only contain safe fields.
No Authorization header should be generated by this bridge.
No Bearer token should be generated by this bridge.

## R16 possible implementation pattern

If fetch callsites exist in static UI, add a small request helper:

```js
function withBusinessOSCivilizationHeaders(init) {
  var next = init || {};
  var existing = next.headers || {};
  var contextApi = window.BusinessOSCivilizationContext;
  var contextHeaders = contextApi && typeof contextApi.getHeaders === "function"
    ? contextApi.getHeaders()
    : {};

  return Object.assign({}, next, {
    headers: Object.assign({}, contextHeaders, existing)
  });
}
```

Then pass it only to existing fetch calls:

```js
fetch(url, withBusinessOSCivilizationHeaders({ method: "GET" }))
```

For POST-capable paths, R16 may patch code structure, but must not execute API POST.
